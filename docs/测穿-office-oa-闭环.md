## 一、闭环长什么样

```
office-oa（被测系统 SUT，:3200）
        ▲  HTTP
        │
api-test-platform（测试平台，:3001）
  ├─ 用例链：登录抽 token → 建单抽 id → 审批 → 登出作废
  ├─ 断言引擎：状态码 / 响应包含 / JSONPath / 耗时上限
  └─ runs 表 + 报告页：每次结果留痕
```

三条命令复现：

```bash
# ① 被测系统重置到种子态并起进程（⚠️ 必须是新进程，见第三节发现一）
cd office-oa && node seed.js --force && node index.js
# ② 把 OA 用例写进平台（幂等，可反复跑）+ 定义并选中「当前环境」
cd api-test-platform && npm run seed:oa
# ③ 让平台去打 OA（会先把「当前环境」打印出来 —— 用例里是 {{base}}，不看这行就不知道在打谁）
npm run test:oa          # 等价于 POST /api/run-all {"prefix":"OA-"}
```

⚠️ **闭环要两个进程同时在**（SUT + 平台）。少一个的症状是脚本报 `fetch failed`，
看起来像「被测系统挂了」—— 实际上是平台没起。别急着怀疑业务代码。

💡 **`OA_BASE` 现在只用来定义环境，不再烤进用例**：44 条用例的 URL 全是 `{{base}}/api/...`，
运行时按平台的「当前环境」替换。想打另一个地址就 `OA_BASE=http://... npm run seed:oa`（只改环境），
用例一个字都不用动 —— 实测把地址指到一个空端口，44 条会**集体失败**且 `run-oa` 打出
「⚠️ 与 OA_BASE 不一致，平台实际打的是 …」，一眼能分清是「配错了」还是「系统坏了」。

## 二、52 条用例在测什么

整套是**一条链**：不是 52 个互不相干的请求，而是 52 步串起来的一次业务闭环。

| 段 | 用例 | 测的设计点 |
|---|---|---|
| A 入口 | OA-01～04 | 健康检查 / 未登录 401 / 伪造 token 401 / **未登录访问不存在的接口也返 401（不泄漏接口是否存在）** |
| B 鉴权 | OA-05～11 | 登录抽 token / 密码错 401 / 缺字段 400 / 带 token 读上下文 / **普通员工读员工列表 403（纵向越权）** |
| C 建单 | OA-12～15 | 非法类型 400 / 缺标题 400 / 建草稿 201 并**抽出单据 id** / 提交转 pending |
| D 审批 | OA-16～24 | 自批 403 / **外部门经理 403（部门收敛）** / 本部门经理通过归档 ★ / **归档后 409** / **无关人员 403** / 不存在的单 404 |
| E 安全 | OA-25～29 | 未授权取附件 401 / 越权取不存在附件 404 / **登出后再用旧 token 401（登出即作废）** |
| F 附件边界面 | OA-30～36 | 未登录列附件 401 / 申请人看自己草稿 200 / **外部门经理看别人单据 403** / **给不存在的单据传附件 404（父资源先于 body 校验）** / 用 JSON 传附件 400 / 删除不存在的附件 404 |
| G 附件全生命周期 | OA-37～44 | **真发 multipart 上传 PNG → 201**（mime 由服务端按字节判出）/ 列表 total=1 / **下载回读字节一致** / **伪装成 PNG 的 exe → 400（只认字节不认名字）** / **已归档单据：本人 409 vs 非申请人 403（成对）** / 删除 200 / 列表回 0 |
| H 站内通知（M3） | OA-45～52 | 提交后审批人未读>0（**引擎挂钩真的触发了**）/ 审批人收件箱含本单 `task` / 申请人收件箱含 `approved` 且 `round=1` 快照 / **外部门经理收件箱空（收件人隔离，不是前端过滤）** / 标已读返回 `read` 且 `unread` 归零 / 重复标已读幂等 / **他人 token 标我的通知 404（和不存在同一口径）** / 申请人标审批人通知 404 |

⭐ 带星号的断言是对应核心设计的：`OA-18 部门收敛`、`OA-20 或签归档`、`OA-23 授权先于状态`、`OA-29 token 黑名单`、`OA-33 附件可见性`、`OA-42 附件上的授权先于状态`、`OA-45 引擎挂钩触发通知`、`OA-48 通知收件人隔离`、`OA-51 通知写路径统一 404`。

**id 不是写死的**：`OA-14` 从建单响应里 `extract rid=$.id`，后面所有审批用例用 `{{rid}}` ——
所以套件每跑一次都自己造数据，不依赖库里现成的单据号，也不会因为库被重置而失效。
第二轮又用同样的手法新建了 `{{rid2}}` 专门给附件用例当靶子（`OA-31`）；
第三轮再从上传响应里 `extract aid=$.id`，把「上传的那一个附件」串到下载/删除上 ——
**同一条链里现在有两个自造的靶子（单据 + 附件），全部现场生成。**

## 三、⭐ 七个真实发现（比「52 条全绿」值钱）

### 发现一：端口上挂着旧进程，差点把两个好功能判成坏的

第一次跑之前手工探针，`exe01`（外部门经理）**批成功了**、登出后旧 token **还能用** ——
两项都是 M2 刚做的功能，看起来双双失效。差点就得出「dept_scoped 和 token 黑名单都不工作」的结论。

真实原因：**3200 端口上是 M2 之前的旧进程**（我启动时被 `EADDRINUSE` 挡回，用的是上一轮的遗留实例）。
判据（很便宜，值得记住）：

```bash
MSYS_NO_PATHCONV=1 netstat -ano | grep ":3200" | grep LISTENING   # 谁在监听
curl -s --noproxy "*" $B/api/attachments/1 -H "Authorization: Bearer $T"
#   旧代码 → {"error":"接口不存在：GET /api/attachments/1"}   ← 路由压根没注册
#   新代码 → {"error":"附件不存在"}                          ← 路由在，只是没这个资源
```

杀掉重启后，两条断言立刻变绿。

→ **教训**：**「功能不生效」和「跑的是旧代码」在现象上完全一样。** 先确认你打的是哪个进程，再怀疑代码。
→ 这也是套件里 `OA-26` 存在的意义：它就是那个哨兵，旧进程会让它必红。

### 发现二：平台自己的断言引擎有语义坑，被真用例逼出来

`OA-08` 断言「管理员权限列表里有 `user:read`」，写成 `$.permissions[*]` + `op: contains` —— **红了**。
但 OA 没错：admin 的权限数组确实含 `user:read`，只是它排在第七位，而引擎在多匹配时**只看第一个**匹配值
（第一个是 `announcement:write`）。

→ 修复：`contains` 在多匹配时改成「**任一**命中即通过」，这才符合「数组里包含某元素」的直觉
（Postman 的 `to.include` 也是这个语义）。其余操作符（`eq/gt/…`）仍是首个匹配值，并在代码注释里写明。
→ 顺手把失败提示从「实际 X」改成「匹配 N 个，首个 X」—— 排障时能一眼看出是「没匹配到」还是「匹配到了但值不对」。
→ **教训**：**光测「自己的平台能跑」，永远发现不了这类语义坑；拿一个真系统去打它才会。**
→ 这条对面试特别有用：它说明我既是被测系统的作者、又是测试平台的作者，**两边都能改**，而发现的 bug 属于**工具**而非**被测物**。

### 发现三：成对断言才能证明「授权先于状态」

单看一条「无关人员审批 → 403」证明不了什么（本来就不该让他批）。
真正证明这条设计的是**同一张已归档单据上的两条断言**：

| 用例 | 谁 | 期望 | 说明 |
|---|---|---|---|
| `OA-21` | 本部门经理（**是**这张单的审批人） | `409` | 有身份 → 才轮到谈状态 |
| `OA-23` | 人事经理（**不是**这张单的审批人） | `403` | 没有身份 → 状态根本不告诉你 |

如果顺序写反（先判状态），无关人员会收到 409 —— 那等于送出一个「这张单存在、且已归档」的探针。
**一条 403 是规定，两条成对才是设计。**

### 发现四：平台执行器只发 JSON —— 能力边界是**先承认、再补掉**的

写第二轮附件用例时才发现：平台的执行引擎是 `JSON.stringify(body)`，**发不出 `multipart/form-data`**。
也就是说「上传一个文件」这件事，平台**根本做不到**，跟写得对不对无关。

两条路：
- a) 扩执行器（加 body 类型 / 文件字段 / 自动 boundary）—— 能让平台真的传文件；
- b) 承认边界，把**不看 body 的那些分支**交给平台，真传文件的部分交给更底层的测试。

**第二轮选的 b**：平台覆盖 `OA-30～36`（401 守卫在前 / 404 父资源先判 / 403 可见性 / 400 非 multipart），
真正传文件、嗅探魔数、大小临界、并发上限那一半交给 office-oa 的 vitest（专项 13 条 + 总数 161）和 Playwright。

→ **教训**：说「测试平台覆盖率」之前，先能说清**它的能力边界在哪**。
  一个只会发 JSON 的执行器 + 一个只收 multipart 的接口，这个组合如果不写下来，下次还会有人以为测过了。
→ 顺带一个可讲的取舍：`OA-35 用 JSON 传附件 → 400` 这条用例，本质是**把平台的短板写成一条断言**。

**第三轮把它补掉了（M8）**。补的过程比结论更值得讲，因为它体现了「测试 → 工具 → 再测试」这个循环：

| 步骤 | 做了什么 |
|---|---|
| ① 扩执行器 | 用例新增 `bodyType`（json / raw / form-data）+ `files`（文件字段）；form-data 时**执行器接管 `Content-Type`（带 boundary）和 `Content-Length`**，用例里手填的那个会被覆盖 |
| ② 不做第三方依赖 | multipart 包体是手搓的（boundary / CRLF / 结尾 `--` / 二进制安全），符合本项目「除 Fastify 系不引库」的基调 |
| ③ 夹具内置在代码里 | PNG / PDF / 伪装 exe（MZ 头）三份小字节直接写进 `src/fixtures.js`。理由：**自动化要的是可重复** —— 每次跑都发一模一样的字节，`size == 41` 这种断言才站得住；而字节内容刻意与 office-oa 的测试夹具一致 |
| ④ 前端跟着改 | 用例编辑器加「请求体类型」下拉 + form-data 时的文件字段表（字段名 / 夹具 / 文件名），选项从 `/api/meta/body-options` 取 —— **唯一事实来源在后端**，不在前端硬编码 |
| ⑤ 自测 | 平台自己加了 15 条测试（`tests/multipart.test.js`），其中含**真发包**的集成测试：起一个 Fastify 收原始字节，断言 boundary、结尾、二进制逐字节到达。平台测试 70 → **85** |
| ⑥ 再回去测 SUT | `OA-37～44` 上线，44/44 一次全绿 |

→ 这里有个**很典型的坑**值得单独记：真机验证时从 `/cases/1/edit` 切到 `/cases/new`，
  Vue 复用了同一个组件实例，`onMounted` 不重触发，**表单里残留着上一条用例的 `bodyType=form-data`** ——
  新建页凭空显示出了「文件字段」。修法是 `watch(() => id, load)` + `resetForm()`。
  这类 bug 单测抓不到、`vite build` 也不报错，只有**真机走一遍**才会露头。
→ **结论**：一条写进文档的「能力边界」不是终点。它是**下一轮的工作项**。
  边界在代码里消掉之后，剩下的才叫真的覆盖到了。

### 发现五：变量缺失的提示，被异常分支吃掉了

第四轮把用例 URL 改成 `{{base}}` 之后，顺手补了「没有当前环境时应当报什么」的测试，结果红了 ——
但**被测系统没问题，红的是平台的报错信息**：

```
期望：detail 里出现「未赋值变量：{{base}}」
实际：Failed to parse URL from /whoami
```

原因：`{{base}}` 没赋值时被替换成空串，url 变成 `/whoami`，`fetch` 直接抛异常 →
走 catch 分支 → 而那段代码只写了 `detail: [e.message]`，
**把「谁没赋值」这条最有用的线索丢在成功分支里了**。

→ 修法：把 `missingNote` 的计算提到**发请求之前**，catch 分支里也带上它（放在第一条，先看变量再看原始报错）。
→ **教训**：**最需要提示的人，恰好是收不到提示的人** —— 变量缺失最常见的后果就是请求发不出去，
  而报错路径往往是最少被测试覆盖的那条。写 catch 的时候问一句「这条路上的人需要知道什么」。

### 发现六：一个会撒谎的环境徽标（真机验证抓出来的）

给平台加了「当前环境」徽标（页头那个 🌐 标签）之后，我在真机浏览器里点了一遍：
**在环境页里点「取消当前环境」，头部徽标纹丝不动**，还显示着刚才那个环境。

原因很典型：徽标画在 `App.vue`（外壳），切环境发生在 `Environments.vue`（子页面），
两处各读各的状态，靠「路由变化时重取一次」来对齐 —— 而**在同一页里切环境根本不会引起路由变化**。

→ 修法：把当前环境抽成共享的 reactive 状态（`web/src/env.js`，跟 `auth.js` 的 `session` 同一套路），
  谁改谁 set，外壳直接读。
→ **教训**：**一个会撒谎的状态显示，比没有这个显示更危险** —— 徽标写着「打测试环境」而平台其实在打别的地址，
  比根本不显示环境名更容易让人犯错。凡是「全局状态 + 多页面读写」的组合，先问一句：**谁负责让它同步？**

**这条缺陷现在有回归网**：`node scripts/m9-env-ui-check.mjs` 在真机 Chrome 里把整条路径点一遍（13 条断言）——
进环境页 → 点「取消当前环境」→ **立刻核对页头徽标变成「未选环境」** → 点「设为当前」核对徽标恢复 →
新建一个临时环境并切过去核对徽标跟着换 → 删掉「正在使用中」的环境核对徽标回落 →
**收尾把当前环境还原并删掉临时环境**（脚本跑完不留副作用，紧接着 `npm run test:oa` 仍是 44/44）。

> ⚠️ 写这个脚本时踩了个坑，值得记：往 `localStorage` 写了 token，页面却还是被弹回登录页，而且 **token 不见了**。
> 两个原因叠在一起：① `auth.js` 的 `session.token` 是**模块加载时**从 localStorage 读一次的 ——
> 只写不重载，session 还是空的 → axios 不带 `Authorization` → 401 → 拦截器 `clearSession()` 把刚写进去的 token 抹掉；
> ② `Page.reload` 是**异步**的，紧接着发 `Page.navigate` 会跟重载竞态。
> **教训：自动化脚本报「超时」时，先把现场打出来（URL / token 在不在 / 页面正文），否则永远在猜。**

### 发现七：把某个值从「固定」变成「可配」，就等于给自己挖了个可观测性的坑

第四轮（M9）刚把被测地址做成可切换的，第五轮一开报告就卡住了：
**报告里只有通过率和用例名，答不出「这个通过率是在哪个地址上跑出来的」。**

在地址写死的年代这不算问题 —— 反正只有一个地址，不说也知道。可地址一旦变成可配的，
**每一条不写清「当时用的是哪个值」的历史记录，都变得无法解释**。
说得更狠一点：一个跑了 557 次、通过率 92% 的汇总，如果不知道它跨了几个环境，这个数字**什么都不能说明**。

→ 修法不是「显示得更清楚」，而是**在执行记录里存快照**：`runs` 加 `env_name` + `base_url`（执行当时的名字与地址），
  而不是只存一个指向环境的 `env_id`。只存外键的话，地址改一次（本地 → 预发），
  历史记录就被**反向改写**成了「它从没打过的地址」。
→ 报告新增「按运行环境汇总」，分组键用快照 → 地址改过之后**自然分成两组**，「换个环境就全红」一眼可见。
→ 老记录（没有这三列）归到「(未记录环境)」一组，**不编造**环境名。本机实测是 557 条 ——
  一打开报告就能看到这一组，本身就是迁移的留痕。

→ **教训**：**配置是活的，历史是死的。** 把任何值从写死变成可配的那一刻，
  就要同时问一句「以后我怎么知道某次运行用的是哪个值」。这条和 office-oa 的 `flow_snapshot`
  （改流程模板不影响在途单据）是**同一条教训的两次独立出现** —— 一次在 SUT 里，一次在我的工具里。

## 四、为了让闭环成立，平台补了什么

原来的平台只能测公开接口 —— 因为 runner 一次只发一个请求，**没法把登录拿到的 token 带到下一个用例**。
没有这一层，「用平台测穿一个真系统」就是句空话。补了：

| 能力 | 做法 | 取舍 |
|---|---|---|
| **用例链** | ① url/headers/body 支持 `{{var}}` ② 用例声明 `extract`（JSONPath 从本用例响应抽值）③ `run-all` 共享一个变量袋 | 变量袋**只在内存**，不落库：token 不该进库，也不该跨运行复用（否则会拿过期 token 假装通过） |
| **链的顺序** | `run-all` 按「创建顺序」（id 升序）跑 —— 界面上的 `listCases()` 是倒序（新的在前），链必须翻过来 | 单跑一条不参与链；有链式依赖的用例不该挂定时任务 |
| **分组** | `POST /api/run-all {"prefix":"OA-"}` 只跑一组 | 用例分组的最小实现；平台里同时挂着示例用例（打外网），不分组的「跑全部」会把别人的红算到自己头上 |
| **缺失变量提示** | 变量没赋值**不判失败**，但 detail 里写明「未赋值变量：{{token}} —— 请用全部运行」 | 缺变量时请求本来就会失败，两处都报会让人分不清真正原因 |
| **请求体类型 + 文件夹具**（M8） | 用例声明 `bodyType`（json / raw / form-data）与 `files`；form-data 时执行器自己搓包体并**接管** `Content-Type`（带 boundary）/ `Content-Length` | 见发现四。夹具**内置在代码里**而不是让用户传文件：自动化要的是「每次跑发一模一样的字节」，`size == 41` 这种断言才站得住 |
| **环境变量集**（M9） | 环境 = `{name, baseUrl, headers, vars}`，用例里写 `{{base}}`；**同一时刻只有一个当前环境**，存在 `settings` 表的一行里 | 见发现五、六。两个关键优先级：环境变量是**基线**（链上 `extract` 抽到的值优先）、环境头是**默认值**（用例手写的同名头优先）；当前环境放一行 KV 而不是 `is_active` 列，是为了不可能出现「两行都 active」 |
| **运行快照**（M10） | 每次运行落库时，把**当时**的 `env_name` / `base_url` 一并抄进 `runs` 行；报告按快照分组（`byEnv`） | 见发现七。环境集是**活的**（改一行全局生效），历史必须是**死的** —— 只存 `env_id` 会让「地址改一次」反向改写历史，一个跨了好几个环境的通过率从此无法解释；老记录归「(未记录环境)」，不编造 |

## 五、第二轮在 SUT 侧顺带抓到一个真缺陷：并发能绕过附件数量上限

`OA-31` 造了张草稿当靶子之后，给附件补了一轮「越权 / 并发 / 边界」的 vitest（`tests/attachments-edge.test.js`，13 条）。
其中一条直接把 OA 自己的 bug 抓了出来：

```js
// 上限设成 2，5 个请求同时发
process.env.MAX_FILES_PER_REQUEST = '2'
await Promise.all([0,1,2,3,4].map(i => uploadAttachment(app, token, id, `c${i}.png`, PNG_BYTES)))
// 结果：落库 5 条 —— 上限被穿了个洞
```

原因是最经典的 **TOCTOU**：`SELECT COUNT(*)` 和 `INSERT` 之间隔着 `await part.toBuffer()`，
5 个请求都读到「现在有 0 个」，于是全部放行。

修法跟项目里既有的并发防线同一套路子 —— **把「数一遍」和「插一行」压进同一条 SQL**，再把判定收敛到 `changes`：

```sql
INSERT INTO attachments (request_id, uploader_id, original_name, stored_name, mime, size)
SELECT ?, ?, ?, ?, ?, ?
WHERE (SELECT COUNT(*) FROM attachments WHERE request_id = ?) < ?
```

`info.changes === 0` → 400，并且**把刚落的盘收回去**（否则磁盘留下没人认领的孤儿文件）。

→ 修完 `rows <= 2`，且「本用例新增的落盘文件数 == 真正入库的条数」。
→ **这说明两层测试分工不一样**：平台那层（黑盒、串行）擅长证明「门锁在不在」；
   **并发这种要靠能控制时序的白盒测试** —— 换句话说，`Promise.all` + 内存库，比发真实 HTTP 更容易把竞态稳定复现。
→ 也顺手把这类「先查后写」的写法记成一条检查项：**凡是「先数一次/先查一次，再写」的地方，都要问一句并发下还成立吗。**

## 六、诚实边界（不做的部分）

- **不做数据清理**：套件每跑一次会真造两张单据 + 一个附件（走完生命周期会自己删掉）。跑完想回到干净状态就 `node seed.js --force`。
- **不做「多环境并行」**：同一时刻只有一个当前环境，`run-all` 就是拿它跑。
  真的需要「一次跑遍三套环境」，应该在外面套一层（分别切环境跑三次），而不是让一次运行同时打多个地址 ——
  那样报告里「哪条失败属于哪个环境」会变成一团浆糊。
- **环境变量不做加密存储**：环境里可以放 token / 灰度头，但它们**明文存在 sqlite 里**。
  自用工具够用；真要放生产密钥，得先有密钥管理（这是明确不做的，不是忘了）。
- **夹具只支持内置的三份，不支持用 URL 或本地路径当夹具**：`bodyType=form-data` 的文件要么引用内置夹具名，
  要么内联 `base64`。**刻意不做**「让用户上传一个文件当夹具」—— 那会让「跑绿了」依赖于运行机器上恰好有那个文件，
  换个环境就红，等于把自动化变成一次性脚本。
- **不做「非图片/非 PDF」的魔数用例泛化**：OA 白名单只有 PNG / JPEG / GIF / WebP / PDF，平台夹具也只做这三份够用的。
  再往下就是给被测系统写测试，不是给平台加能力。
- **不做用例版本管理 / 断言脚本**：断言是**声明式**的（JSONPath + 操作符），不支持写 JS 前后置脚本。
  这是刻意的：声明式好用、好收录，也正好是「不引第三方库」的延续。
- **不做并发压测**：平台的链是顺序执行的（顺序是用例链的前提，不能改成并发）。
  并发相关的验证在 office-oa 的 vitest 层做 —— 附件数量上限那个 TOCTOU 缺陷就是这么抓出来的，
  而且**这一层平台替不了**：`Promise.all` + 内存库比发真实 HTTP 更容易把竞态稳定复现。
- **平台自身的鉴权开关不做进产品**：平台有 `API_AUTH_DISABLED`（给测试用），OA 那边**故意没有**
  —— OA 是拿来练越权测试的，一个旁路开关会让测试全绿、生产裸奔。

## 七、面试怎么讲（一段话）

> 「我写了两个东西：一个专门用来被测试的 OA，和一个测试平台。
> 但『平台能测 OA』这件事我一开始只是写在文档里 —— 真去跑的时候发现，平台连需要登录的接口都测不了，
> 因为执行引擎一次只发一个请求，登录拿到的 token 传不到下一个用例。所以我先给平台补了**用例链**：
> 用例里能写 `{{token}}`，能从响应里按 JSONPath 抽值，跑全部时按创建顺序共享一个变量袋。
> 补完一跑，29 条里红了 1 条 —— **红的是我的平台，不是被测系统**：JSONPath 多匹配时 `contains` 只看第一个元素，
> 所以『权限数组里有没有 user:read』会假失败。
> 后来我再补附件那一段，又撞到一个更根本的东西：**平台的执行器只会发 JSON，附件接口只收 multipart**，
> 所以『上传文件』这件事平台压根做不到。我没有硬凑一个看起来绿色的报告，而是把不看 body 的分支
> （守卫、父资源、可见性）交给平台，真传文件的部分交给 vitest 和 Playwright —— 并且把这条边界写进文档。
> 但我没停在这儿：**那条边界后来被我当成一个工作项做掉了** —— 给用例加上请求体类型和文件字段，
> multipart 包体手搓（不引库），夹具的字节直接写进代码（因为自动化要可重复，`size==41` 这种断言才立得住）。
> 补完再跑，附件那一段从『平台发不出』变成 8 条真跑过的断言，44 条全绿。
> 顺带在真机验证时抓到一个纯前端的坑：从编辑页切到新建页，Vue 复用了组件实例，
> 表单里残留着上一条的 `bodyType` —— 单测和 build 都不报错，只有真机走一遍才看得见。
> 再往后，附件那轮用例在 OA 自己身上抓到一个真 bug：数量上限能被并发绕过，
> 因为『先数一遍再插入』中间隔着一次 await。改成一条带子查询的条件插入才真正守住。
> 最近这一轮我做的是**把被测地址从用例里搬出去**：44 条 URL 一律写 `{{base}}`，
> 地址由平台上的『环境变量集』提供，换环境不用重写用例 —— 做完顺手又抓到两个平台自己的毛病：
> 一个是**变量缺失的提示被 catch 分支吃掉了**（最需要提示的人恰好收不到提示），
> 另一个是**页头的环境徽标在同一页里切环境后不刷新**（一个会撒谎的状态显示，比没有这个显示更危险）。
> 这两个都不是被测系统的 bug，是我的工具的问题 —— 而它们都是**被『换一个环境跑一遍』这个真实需求逼出来的**。
>
> 最近这一轮我没再往被测面上加东西，而是回头补「这套资产本身能不能带走」：
> 做了**套件导出/导入** —— 导出成 JSON，不带头也不带 id（换个库导入要重新发号），
> 用例按**创建顺序**排（导出顺序就是串链顺序），导入时坏条目单独记进 `failed` 而不整份打回，
> 冲突给了 rename / overwrite / skip 三种策略、默认 rename。
> 这件事又逼出一个我原本想不到的坑：我给请求头脱敏是按「键名敏感」判的，结果把 `X-Token: {{token}}` 这种
> **变量引用**也抹成了空串 —— 导到别的机器上第二条用例不带 token，链**静默断掉**（导出文件打开看还挺正常）。
> 是我先写了一条「导出 → 清空库 → 导入 → 再跑一遍」的端到端用例，**它先红了才发现的**；
> 判据最后改成「键名敏感**且**值是字面量才抹」。
> 所以我现在的看法是：**「能导出」这种看起来纯搬运的功能，真正的验收不在导出那一刻，而在导出之后还能不能跑。**
> 整个过程里我最想讲的是第一次手工验证：我以为刚做的两个安全功能都失效了，
> 查下来是**端口上挂着旧进程** —— 『功能不生效』和『跑的是旧代码』在现象上一模一样。

> 再往后我给 office-oa 本身加了**站内通知（M3）**：消息中心 + 收件人隔离 + 引擎同事务挂钩。这一步反过来喂回了闭环 —— 平台套件顺势扩到 **52 条**，新增的 OA-45～52 把『引擎挂钩真的触发了通知』『收件人隔离（不是前端过滤）』『轮次是事件快照』『标已读幂等』『写路径统一 404』都钉成可重复断言。它顺便又抓出一个平台侧的断言写法坑：模板变量 `{{rid}}` 替换后是字符串，而 `requestId` 是数字，严格比较会假失败 —— 这种『类型不对齐』在单测里不会被发现，只有真去跑业务链才暴露。
> 那一刻我才真正理解，为什么测试报告必须写清『被测版本』。」
